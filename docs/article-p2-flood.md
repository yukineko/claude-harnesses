## はじめに

Claude Code 用のハーネス（hook・gate・skill の詰め合わせ）を Rust のモノレポで自作している。
このハーネスでは、敵対的レビュー（finder と verifier を別 agent に分けた、GAN 的な監査）や、
セッション中に行う監査が、見つけた問題を backlog に積んでいく。

その backlog が、**P2（低優先度）の課題で溢れた**。

P2 は間違っていたわけではない。ただ、**証拠がなく、小さかった**。
それでも数が多いと、token を使う優先順位が狂い、本来の問題が後回しになる。

この記事では、backlog の 1,643 件を実測し、原因と対策を検証する。
そして、対策そのものをテストで検証したら、肝心の経路が未対応だった、という話までを書く。

数字はすべて、git 管理下の backlog store を 2026-10-15（測定点 `9c7a54d5`）に集計したもので、
付録のスクリプトで再現できる。

---

## 1. 症状: P2 が一番多く、一番実を結ばない

| 優先度 | 件数 | 修正を観測（F→P） | 証拠なしで破棄 |
|---|---|---|---|
| P0 | 136 | 0 | 0 |
| P1 | 645 | 70（10.9%） | 85（13%） |
| **P2** | **698** | **8（1.1%）** | **310（44%）** |
| P3 | 65 | 0 | 49（75%） |

「修正を観測（F→P）」は、修正前の rev ではテストが落ち、HEAD では通ったことを backlog が記録した件である。
この仕組みは 10 月に入ったので、P0 が 0 件なのは時期の影響を受けている。

P2 は全体の 42% を占め、P1 より多い。それなのに、修正が観測で確かめられたのは 8 件だけだった。

10 月には、作成件数で P2 が P1 を逆転した。

| 作成月 | P1 | P2 | P2/P1 |
|---|---|---|---|
| 7月 | 146 | 118 | 0.81 |
| 8月 | 131 | 75 | 0.57 |
| 9月 | 243 | 201 | 0.83 |
| 10月 | 93 | 265 | **2.85** |

さらに、done になった P2/P3 は 287 件あり、そのうち **241 件（84%）は、より古い P0/P1 が未解決のまま閉じられていた**。
P2 は見つかるだけでなく、直す作業にも token を使っていた。

ある 12 日間だけは P1 が優先されていた（閉じたのは P1 が 67 件、P2 が 7 件）。
ただしそれは、人間が flow に「P1 をやれ」と指示したからである。仕組みが自分でそう選んだのではない。
**自動で回すと、見つけたものを追いかけ続け、問題を見失う。**

---

## 2. 最初の仮説は「見つけたい欲」だった

最初は、GAN や監査の「発見したい欲」が強すぎるせいだと考えた。

半分は当たっている。finder は偽陽性を出しても何も払わない。
「問題を探せ」というプロンプトには「問題がある」という前提が入っていて、LLM は「何もない」と答えにくい。

ただ、データを見ると、効いているのは欲の強さではなく構造だった。

### 出すのはタダで、消すのは高い

本物の GAN では、discriminator が間違えると罰を受ける。この finder にはそれが無い。
出すのはタダで、記録・triage・裁定・破棄のコストは、すべて後工程が払う。

### 積み上がる一方で、修正では一度も減らなかった

| 月 | 作成 | done | cancel | 月末の未解決 |
|---|---|---|---|---|
| 6月 | 81 | 59 | 0 | 22 |
| 7月 | 352 | 238 | 6 | 130 |
| 8月 | 276 | 40 | 1 | 365 |
| 9月 | 528 | 428 | 11 | 454 |
| 10月 | 406 | 169 | 622 | 69 |

未解決は 9 月まで毎月増えた。**修正によって減った月は一度もない。**
減ったのは、10-03（149 件）と 10-15（461 件）の 2 回の一括破棄だけである。

### 検証が、新しい finding を生む

1,643 件のうち **620 件（38%）が、以前の backlog item を参照**していた。参照をたどった連鎖は、深さ 2 以上が 181 件ある。
一番深い連鎖はこうだった。

```
625aa170 P2  並列作業の runtime conflict 検知（機能追加）
 └ 91b4a26b P2  625aa170 follow-up
   └ e117d351 P2  91b4a26b (v2)
     └ 7a1beb86 P2  merge-hold liveness
       └ 617b3112 P0  merge gate の fail-open
         └ 7fb00031 P1  merge() が conflict 記録の失敗をログだけで流す
```

一つ一つのステップは正しい対応である。ただ、6 段たどったあとで「もともと何を解きたかったのか」と問う手順は、どこにも無かった。

## 3. 「間違い」ではない。証拠がなく、小さいだけ

P2 を「間違い」と「些少」に分けようとしたら、人間に訂正された。

> 間違っているわけではない。ただ証拠がない、問題が小さい。そこにこだわると、本来の問題を解決できず、ROI が低くなる。

データもそれを支持した。10-04 に「unproven」として閉じた 12 件は、テストを書くと HEAD で通ったか、テストで測れないものだった。
主張が間違っていたのではなく、すでに直っていたか、測る手段が無かったのである。

今朝（10-15）の一括破棄はこうだった。

- 破棄は 461 件。主な理由は「RED の証拠が記録されていない」
- そのうち、再現テストを試した記録があるのは **1 件だけ**
- notes の合計は **約 41.7 万字**（調査に使った token は別にかかっていて、測れていない）
- 内訳は P2 が 298 件（65%）、P1 が 85 件、P3 が 49 件、優先度なしが 29 件

**証拠を出せないものを課題に上げること自体が、迷惑である。** 記録され、triage され、裁定され、一括破棄されるまで、触られるたびに token を食う。

---

## 4. 反論: では、検証は要らないのか

主張を「GAN の結果は、検証しないとゴミが積み上がる」に絞り、反論を当ててみた。

| 反論 | 判定 | 根拠 |
|---|---|---|
| 積み上がっても、優先順位さえ守れば無害 | 退けられる | 上の 241/287 件。しかも backlog は毎セッション context に注入されるので、量があるだけで token を食う |
| P0 を逃すコストに比べれば、錯誤は安い | 重要度による | P0 級なら正しい。P2 は修正の観測率が 1.1% で、取りこぼしても損失は小さい |
| 検証するより、直してしまう方が安い | 一部成り立つ | doc の行番号ずれ程度なら。ただし、錯誤を「直す」と不要な変更が入る |
| 検証も間違える | 成り立つ（最も強い） | 根拠なしの棄却を禁じると、反証できない UNVERIFIED がキューに残り続ける |
| 錯誤にも学習価値がある | 部分的 | その価値は finder ごとの精度という統計に出る。1 件ずつタスクにしなくても得られる |

主張の核は崩れない。どの反論も「検証が要らない」までは届かない。
ただし検証も誤るので、**検証を挟むだけでは積み上がりは止まらない**。反証できなかったものを流し出す出口まで決めて、初めて閉じる。

そして、**GAN そのものは悪ではない**。修正を観測できた 78 件のうち 75 件は、監査が見つけたものだった。
本物を見つける主な手段は GAN である。悪いのは、**検証せずにタスクにすること**だ。

---

## 5. 設計: テストで再現できたものだけを課題にする

答えは「欲を抑える」ではなかった。**finding を出す側に、証拠のコストを払わせる**ことだった。

1. GAN の結果は、すべて記録する（捨てない）
2. 利害関係のない、別 context の別 agent が、再現テストを書く
3. そのテストが HEAD で**挙動として失敗した**ときだけ、backlog のタスクにする
4. 再現しなかったものはタスクにせず、unproven として記録に残す
5. 検証者は判定だけを返し、新しいタスクを生まない

backlog では、これを `backlog add --repro-test <テストを実行するコマンド>` として実装した（2026-10-04）。
`--repro-test` を付けない add はタスクを作らず、exit 2 で終わり、unproven の記録に追記される。

その結果、今の pending 69 件は、**69 件すべてが再現済み**である。そのうち P2 は 36 件ある。
つまり、**P2 が全部要らないわけではない**。再現できた P2 は、ちゃんとキューに残る。

錯誤はテストで再現しないので、タスクにならない。backlog の中で繰り返しコストを生むこともない。
一括破棄で本物を捨ててしまっても、再現テストを付ければ再提出できる。本物なら RED が出て戻ってくるし、錯誤なら戻ってこない。
**選別をテストに任せたので、捨て方が粗くても回復できる。**

---

## 6. 設計そのものを検証したら、GAN 本体の経路が未対応だった

ここで、この設計が本当に動いているかを確かめた。

`backlog add` を呼ぶ箇所を調べると、flow・condukt・scout の skill は `--repro-test` を渡していた。
ところが、continuous-audit（形式の GAN 監査）の CONFIRMED finding を backlog に送る bridge は、渡していなかった。

コードを読んだだけでは予測にすぎない。そこで、利害のない別モデルの agent に再現テストを書かせ、RED を観測した。

| 仮説 | 結果 |
|---|---|
| H1: bridge は、再現テストが実際に失敗していても `--repro-test` を渡さないので、タスクを作れない | RED |
| H2: add が全部拒否されても、bridge は exit 0 で終わり、成功と区別できない | RED |
| H3: continuous-audit のスクリプトは、転送に失敗しても PASS を出す | 予測した経路では GREEN（PARTIAL を出していた）。ただし、bridge が exit 3 で終わる**別の経路**で PASS を出していた |
| H4: `--repro-test` なしの add は unproven に記録される | GREEN（記録の仕組みは動いていた） |

H3 は、コードを読んだ段階の予測が外れた例である。予測のまま直していたら、存在しない欠陥を直し、実在する別の欠陥を見逃していた。

修正した内容は次のとおり。

- bridge は、見つけた回帰テストを `--repro-test` として渡す
- 拒否された add と失敗した add を、JSON の summary で `unproven` と `failed` として数える
- スクリプトは bridge の終了コードも読み、exit 3 を PASS にしない
- 転送が 1 件でも失敗した run は、FAIL を出して exit 1 で終わる

### PARTIAL は存在してはいけない

最後の点は、最初は「PARTIAL（一部失敗）を出して exit 0」にしていた。人間の指摘は短かった。

> そもそも PARTIAL なんてものが存在してはいけないのでは？ 成功じゃないものは失敗。

成功でも失敗でもない第三の状態は、下流から成功と失敗の区別を消す。終了コードしか見ない呼び出し側にとって、exit 0 の PARTIAL は成功である。

PARTIAL を廃止して exit 1 にしたら、既存のテストが 1 本落ちた。そのテストは、転送が実際に失敗していた run を「exit 0 であるべき」と assert していた。
テスト環境の bridge が本物の backlog に届き、それが add を拒否していたのである。**テストの方が、失敗を成功として固定していた。**
テストの環境を、転送を受理する偽の backlog に直し、PASS 行が出ることも assert するようにした。

偽の backlog とは別に、本物の backlog バイナリでも確かめた。使い捨ての worktree で、bridge と同じ形式の `--repro-test` を渡すと、タスクは「filed as pending」になった。

### 捨てた指摘の近くに、本物があった

皮肉なことに、今朝の一括破棄には次の 2 件が含まれていた。

- bridge は、add の拒否を warning として読み飛ばす
- continuous-audit のスクリプトは、転送に失敗しても PASS を出す

**証拠が無いという理由で捨てられた指摘の近くに、本物の欠陥があった。** そして、テストを書いたら RED が出て、修正までたどり着いた。
前節の「捨て方が粗くても回復できる」が、この件で実際に起きた。

## 7. 形式の監査と、場当たりの監査

監査由来の finding は 2 種類あった。

| 種類 | 件数 | 修正を観測 | 破棄 | 10-15 時点で未解決 |
|---|---|---|---|---|
| continuous-audit（finder≠verifier、CONFIRMED のみ送る） | 60 | 2 | 2 | 2（2 件とも破棄） |
| セッション中の場当たりの監査 | 523 | 73 | 202 | 204（201 件を破棄） |

破棄率だけを比べると、形式の監査の方がはるかに良く見える。だが、これは比較として成り立たない。
形式の監査の item は 7 月に作られ、一括破棄の前にほとんど閉じられていたからである。破棄は、その時点で未解決だった item にしか当たらない。

形式の監査の記録では、2026-07-10〜07-22 の 4 ラウンドで、新規 finding が 28 件、CONFIRMED が 23 件、追加された回帰テストが 18 件だった。
最後のラウンドは 07-22 で、それ以降は回っていない。
**P2 の洪水を起こしたのは、場当たりの監査の方だった。**

## 8. 残る穴

正直に書いておく。

- **テストを誰が書いたかは、機械では強制していない。** 「別 context の別 agent が書く」という原則は skill の指示にあるだけで、`backlog add` が見るのは「テストが挙動として落ちるか」だけである
- **token の実額は測れていない。** 1 finding あたりのコストは、notes の文字数という代用指標しかない
- **破棄した 461 件に本物がどれだけ含まれていたかは、判定できない。** 人間の裁定でまとめて閉じたからである。ただし前節のとおり、再現テストを付ければ戻ってこられる

---

## まとめ

- 修正を観測できた欠陥のほとんど（78 件中 75 件）は、GAN（監査）が見つけた。しかし出力の多くは、証拠がなく小さい
- それを検証せずにタスクにすると、修正より登録の方が速くなり、backlog はまとめて捨てない限り減らない
- 自動ループは、新しい finding を深さ優先で追いかけ、ゴールを見失う
- 対策は、欲を抑えることではない。**finding を出す側に、証拠のコストを払わせる**ことである
- GAN の結果はすべて記録する。そのうえで、別 agent が書いた再現テストで RED が観測できたものだけを課題にする
- そして、その設計自体もテストで検証する。この記事を書く途中で、GAN 本体の経路が未対応だったことが見つかった
- 「一部成功」は成功ではない。**成功じゃないものは失敗**として返す

## 付録: 測定の再現

repo root で実行する。store は git 管理下なので、測定点を checkout すれば同じ数字が出る。

```python
import tomllib, collections as C, datetime as D

rows = []
for f in [".backlog/tasks.toml", ".backlog/tasks.done.toml"]:
    rows += tomllib.load(open(f, "rb")).get("task", [])

def pri(t):
    return next((p for p in ["p0", "p1", "p2", "p3"] if p in t["tags"]), "none")

def closure(t):
    return (t.get("closure") or {}).get("reason")

def f2p(t):
    return bool((t.get("closure") or {}).get("red"))

def month(ts):
    return D.datetime.fromtimestamp(ts).strftime("%Y-%m")

# 優先度別: 件数 / F→P / 破棄
for p in ["p0", "p1", "p2", "p3"]:
    rs = [t for t in rows if pri(t) == p]
    print(p, len(rs), sum(map(f2p, rs)), sum(closure(t) == "discard" for t in rs))

# 月別: 作成 / done / cancel / 月末の未解決
o = 0
cr = C.Counter(month(t["created_at"]) for t in rows)
dn = C.Counter(month(t["updated_at"]) for t in rows if t["status"] == "done")
ca = C.Counter(month(t["updated_at"]) for t in rows if t["status"] == "cancelled")
for m in sorted(cr):
    o += cr[m] - dn[m] - ca[m]
    print(m, cr[m], dn[m], ca[m], o)
```
