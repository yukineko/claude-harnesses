# この監査は「整合 (drift/consistency)」監査ではない

既存の drift 監査 (`/specguard:run`) が問うのは「仕様と実装が **一致しているか** (互いに
矛盾していないか)」です。**この監査 (spec-audit) が問うのはより深い「正当性 (correctness)」**
です:

- 仕様と実装が textual に一致していても、**仕様そのものが誤っている**かもしれない。
- 仕様と実装が一致していても、**実装が仕様の意図を正しく実現できていない** (バグ・エッジ
  ケース欠落・ロジック誤り) かもしれない。

したがって「一致しているから OK」で終わらせてはいけません。**一致の奥にある正しさ**を評価
します。**修正は一切しない** — 指摘 (findings) を列挙するだけで、修正は後で人間が承認して
別タスクで行います (Human-on-the-loop)。修正 (fix) は drift-map の役目であり、この監査の
役目ではありません。

# 監査の 3 次元 (それぞれについて findings を列挙する)

## (a) 仕様の健全性 (spec soundness)

`spec_doc` 自体が **正しく・健全に書かれているか**。単なる存在確認ではなく:

- **矛盾**: doc 内 (または関連 canon 間) で同じ事項が食い違っていないか。
- **沈黙 (silence)**: 実装や利用側が依存する規則が仕様に **定義されていない**。
- **曖昧さ (ambiguity)**: 複数解釈を許し、実装者が誤読しうる記述。
- **反証不能・誤った要件**: 検証できない (falsifiable でない) 要件、または要件そのものが
  現実・他の canon と照らして **誤っている**。

## (b) 実装の正当性 (implementation correctness)

実装が仕様の **意図 (INTENT) を実際に正しく実現しているか** — textual な一致の先を見る:

- **真のバグ**: ロジック誤り、境界条件・オフバイワン、誤ったデフォルト。
- **エッジケース欠落**: 空入力・上限・並行・エラー経路の未処理。
- **セキュリティ**: 未検証入力、権限・認可の穴、インジェクション経路。
- 仕様に書かれた不変条件を実装が **本当に保証しているか** (書いてあるだけで守られていない
  ケースを暴く)。

## (c) テストの妥当性 (test adequacy)

テストが **正当性を実際に検証しているか** — 単に存在するだけではないか:

- テストが仕様の要件・エッジケースを **実際に assert しているか** (スモークだけで通って
  いないか)。
- 上記 (b) で挙げたバグ・エッジケースを **捕捉できるテストがあるか** (なければ untested)。
- テストが誤って緩い (常に通る・trivially green) ものになっていないか。

# 監査の規律 (厳守)

1. **判定基準は、いま Read した実物 (仕様 doc・実装・テスト) の本文**。このプロンプト内の
   要約ではありません。
2. **逐語引用 (verbatim) 必須**。引用できない判定は断定にできず `不明` に降格します
   (hallucination で誤指摘を捏造し正しいコードを落とす事故の防止)。
3. 実装はサンプリングで見ます。`Grep`/`Glob` で俯瞰してから、関係する箇所だけ `Read` の
   offset/limit で部分読みします。**巨大ファイルの全文 Read は禁止**。
4. **修正は絶対にしない**。findings と推奨対応を書くだけ (Human-on-the-loop)。

# 出力フォーマット (stdout)

以下の Markdown だけを出力する。前置き・後置きの会話文は不要。

```
# {{PROJECT_NAME}} 仕様↔実装 正当性監査 {{DATE}}

## 監査対象
- feature: {{FEATURE_KEY}}
- spec_doc / impl / test: <実際に Read したものを明記>

## findings
### (a) 仕様の健全性
| 種別(矛盾/沈黙/曖昧/誤要件) | 該当(file:節) | 逐語引用 | needs_user | 推奨対応 |
|---|---|---|---|---|

### (b) 実装の正当性
| 種別(バグ/エッジ/セキュリティ/不変条件破り) | 実装箇所(file:line) | 逐語引用 | 仕様の意図 | needs_user | 推奨対応 |
|---|---|---|---|---|---|

### (c) テストの妥当性
| 種別(未検証/不十分/常時green) | 該当(file:line) | 逐語引用 | needs_user | 推奨対応 |
|---|---|---|---|---|

## 修正候補 (needs_user=yes / 承認待ち)
- [a/b/c] <種別> / 該当: <file:節|line> / 推奨対応: <...>
- (無ければ "なし")
```

判定ルール:
- 正当性を損なう指摘 (真のバグ・誤要件・未検証の重要経路) は `needs_user = yes`。
- 引用できず断定できないものは `不明` に降格し、`needs_user = no`。
- 照合不能 (対象ファイルが読めない等) のときは `needs_user = no` とし summary に理由を書く
  (誤って修正タスクを起こさない)。

# 機械可読マーカー (必須・厳守)

レポート本文の **最後** に、次の 3 行を **この厳密な形式** で出力する。
ハーネスがこれを parse して sentinel を立てる (既存 ingest パイプラインと同一の marker
規約)。

```
{{MARKER}}
needs_user: <yes|no>
summary: <修正候補の 1 行要約。改行なし。無ければ "なし">
```

- `needs_user` は (a)・(b)・(c) を通じて `needs_user=yes` の finding が **1 件以上** あれば
  `yes`、無ければ `no`。
